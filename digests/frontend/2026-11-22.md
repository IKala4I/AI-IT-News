## 📱 React Native та Expo

**React Native [виклав 0.89.0-rc.2](https://github.com/facebook/react-native/releases/tag/v0.89.0-rc.2) — і `pod install` тепер свідомо падає на SwiftPM-апках**

Третій RC перед стабільним 0.89. Що змінює поведінку:
• `pod install` фейлиться, якщо апка вже на Swift Package Manager; повернутись на CocoaPods — `react-native spm deinit`, потім `pod install`
• C++ Native Animated (`cxxNativeAnimatedEnabled`) оголосили стабільним; shared animation backend (`useSharedAnimatedBackend`) поки тільки в canary і nightly
• `contentInsetAdjustmentBehavior` на iOS ScrollView більше не додає safe-area інсет і падінг `contentContainerStyle`, а бере більший з двох
• нові `StatusBar.getVerticalBarEdgeIOS()` і `useVerticalBarEdgeIOS()` — під вертикальний бар iPhone Duo
• React DevTools 8.0.0 з панеллю Suspense

⚠️ **Міграція:** зміна `contentInsetAdjustmentBehavior` тихо поїде по скролах, у яких падінг заданий і на контейнері, і через safe area. [Реліз-ноти](https://github.com/facebook/react-native/releases/tag/v0.89.0-rc.2)

Якщо плануєш 0.89 у грудні — цей RC вартий прогону саме через iOS-скроли й SwiftPM, бо обидві зміни видно не з логів, а очима.

**Software Mansion [розповів, як Gobi переїхав](https://swmansion.com/blog/react-native-to-native-migration-gobi/) з React Native на Swift і Kotlin — через React islands**

Друга така історія за два тижні після Shopify, але цінне тут не рішення, а механіка. Нерозмігровані фічі лишались окремими RN root view, зареєстрованими через `AppRegistry` і вмонтованими в нативні екрани та шити. Усі острови шарили один JS-рантайм, який стартував лише коли острів справді потрібен; реєстр островів працював чеклістом міграції, і коли він спорожнів — зняли Hermes, Metro і решту рантайму. Сумісність тримали Turbo Native Module адаптерами і Fabric-компонентами.

Паритет перевіряли дешево: Argent водив апку по екранах і знімав скриншоти, ImageMagick підсвічував піксельні різниці.

Цифри: ~11 тижнів на основний перехід, двоє розробників (по одному на платформу), цільові 120 FPS на мапі. Before/after FPS у статті немає.

Навіть якщо нікуди не переїжджаєш, патерн «острів + контракт на навігацію + скриншот-дифи» — робочий спосіб винести одну гарячу фічу в нативку без переписування всього. Самі автори пишуть, що більшості апок достатньо точкових нативних модулів.

## 🧰 Бібліотеки й тулінг

**Reanimated [зарелізив 4.8.0](https://swmansion.com/changelog/reanimated-4-8-0/) — Shared Element Transitions тепер увімкнені за замовчуванням**

Головна зміна: шарена вʼюшка реально переїжджає між екранами, а не копіюється — тож відеоплеєр чи картинка лишаються живими під час переходу. Переходи ходять за таргетом через нативні стеки, модалки, шити, back-жест, таби і скрольовані списки.

Решта:
• `SharedTransition.fadeContent()` з опціями `fadeOut.end` і `fadeIn.duration`
• вернули API з Reanimated 3: `.custom()`, `.progressAnimation()`, `.defaultTransitionType()`
• `Animated.Text` приймає shared values як children, навіть змішані зі статичним текстом
• `backgroundImage` анімується в CSS-анімаціях і транзишенах; `borderCurve`, `verticalAlign`, `objectFit` стали анімованими
• маппери крутяться лише коли є робота — апка без анімацій іде в idle

⚠️ **Міграція:** RN 0.86 більше не підтримується (тільки 0.87–0.89), потрібні Worklets 0.14.x, а вимикач нової поведінки — `ENABLE_SHARED_ELEMENT_TRANSITIONS: false`. Колбек нерухомого переходу тепер віддає `false` замість `true`. [Реліз-ноти](https://github.com/software-mansion/react-native-reanimated/releases/tag/4.8.0)

Якщо в тебе є `sharedTransitionTag` будь-де — це не рутинний мінор, поведінка зміниться сама собою. Хто сидить на RN 0.86, лишається на 4.7.x.

#libraries

**William Candillon [виклав другу частину Graphite](https://wcandillon.dev/article/hello-graphite-webgpu) — Skia і WebGPU тепер шарять один Dawn-девайс**

Суть: якщо поставити `react-native-webgpu` поруч зі `react-native-skia`, вони працюють на одному інстансі Dawn, і текстури ходять між ними без копій і CPU-readback. Девайс Skia обертається у звичайний `GPUDevice`:

```ts
import { Skia } from "react-native-skia";
import { importDevice } from "react-native-webgpu";

const device = importDevice(Skia.getNativeDevice());
```

Далі `Skia.Image.MakeFromGPUTexture()`, `Skia.Surface.MakeFromGPUTexture()` і `adoptTexture()` зшивають 2D-Skia, Three.js-сцени, камеру і ML-моделі в один пайплайн: у демо Three.js рендериться в текстуру, а Skia кладе на неї backdrop-фільтри і 2D-UI. Платформенні буфери (IOSurface, AHardwareBuffer, YUV) замінили Native Buffer API з v2, а `queue.drawElementImageToTexture()` прийшов на заміну `makeImageFromView()` — автор чесно називає це «best-effort»: на iOS і Android 13+ прямо на GPU, на старшому Android фолбек на CPU із гіршою точністю.

Бенчмарків тут немає, вони були в першій частині.

Поки це для тих, хто реально змішує 2D, 3D і камеру на одному екрані. Але «без CPU-readback» — рівно та штука, через яку такі сцени раніше не тягнули 60 FPS.

**react-native-bottom-sheet від Software Mansion [дійшов до 1.0](https://swmansion.com/changelog/react-native-bottom-sheet-1-0-0/), а через три дні — [до 1.1](https://swmansion.com/changelog/react-native-bottom-sheet-1-1-0/)**

Два тижні тому тут була 0.18 — тепер є перший стабільний. У 1.0 головне — уніфіковані запити на закриття: тап по скриму, dismiss від скрінрідера, Android back і Escape усі кличуть `onCloseRequest`, і шит лишається відкритим, поки хендлер не змінить `index`. Плюс `scrimColor` приймає будь-який `ColorValue`, включно з `PlatformColor` і `DynamicColorIOS`, а детентні `insets` отримали `start`/`end`.

1.1 додала `maxWidth` і `placement` на обидва компоненти (міняються на льоту) і прибрала стрибок останнього кадру при відкритті з нуля на повну висоту.

⚠️ **Міграція з 0.18.1:** `nativeOverlay` на `ModalBottomSheet` перейменували у `windowOverlay`, а `settleDuration` тепер у мілісекундах — явні значення треба помножити на 1000. [Кроки міграції](https://swmansion.com/changelog/react-native-bottom-sheet-1-0-0/)

Це та сама бібліотека, якою Gobi виносив шити в нативку, і тепер у неї є стабільна мажорка. Нижче 1.0 переходити вже немає сенсу — мігруй одразу на 1.1.

**Oxlint [перевів type-aware лінтинг на tsrs](https://oxc.rs/blog/2026-11-17-faster-type-aware-linting-with-tsrs) — порт TypeScript на Rust**

Що робить і що замінює: tsrs — окремий npm-пакет, альтернатива tsgolint як бекенд для типозалежних правил Oxlint. Ставиш обидва, і Oxlint підхоплює його сам:

```sh
pnpm i -D oxlint tsrs
pnpx oxlint --type-aware
```

Додатково `--type-check` змушує один прохід по типах обслуговувати і лінт, і тайпчек.

Цифри від команди Oxc: до 5× швидше за tsgolint v7.0.2007 і ~70% менше памʼяті; у звʼязці лінт плюс тайпчек — до 7× і до 75% менше памʼяті; проти typescript-eslint — до 98×.

Наскільки стабільно: реалізовані всі 61 правило tsgolint v7.0.2007 з тими самими опціями й діагностикою, але автори просять репортити розбіжності у виводі, фіксах і памʼяті, «щоб дійти до стабільного релізу». Серед юзерів називають Cloudflare, Owner.com і OpenAI. Бенчі вендорські, методології в пості немає.

Якщо type-aware лінт у тебе на typescript-eslint і CI через це тягнеться — це найдешевший спосіб перевірити, скільки там насправді запасу.

## 📲 Платформи і стори

**Google Play [ввів adaptive app quality requirements](https://developer.android.com/blog/posts/google-play-adaptive-quality-standards) — з квітня 2027 без них апку не опублікуєш**

Пост від 18 листопада. З квітня 2027 апка мусить відповідати мінімум Tier 3 («Adaptive ready») і мати foldable-скриншоти в листингу:
• Tier 3 — заповнювати весь екран без леттербоксу і compatibility mode, зберігати стан (скрол, інпут, відтворення медіа) при ротації, складанні-розкладанні й ресайзі, працювати в multi-window
• 3 foldable-скриншоти додатково до 2 телефонних: 1:1 внутрішній екран, 4:3 внутрішній плюс 10:16 складений зовнішній
• завантажувати foldable-скриншоти в Play Console можна вже сьогодні
• серпень 2027 — обовʼязковий target API level 37 (Android 17), опт-аути з обмежень orientation і resizability на великих екранах прибирають

Хто не дотягне — не зможе публікувати й оновлюватись, плюс можлива просадка видимості; уже опубліковані необновлювані апки лишаються доступними для завантаження. Для ігор є окремий документ.

![Letterbox states on foldable](https://developer.android.com/static/blog/assets/letterbox_states_foldable_33dc54f480_Z2kPfxi.webp)

Для RN це насамперед про збереження стану при fold/unfold і про те, щоб нічого не ламалось на 1:1 екрані — тестувати на foldable-емуляторі варто починати зараз, а не за рік. Скриншоти — найдешевша частина, її можна закрити хоч завтра.

## 💡 Рецепти

**Рецепт: піднімати хмарний симулятор під конкретний білд PR і не платити за повний ребілд**

Expo [розписав](https://expo.dev/blog/agentic-workflows-with-expo-simulators) три воркфлоу на Expo Simulators, і найкорисніше в пості — конкретні команди.

Запустити симулятор на вже зібраному білді з обмеженням по часу:

```bash
eas simulator:start --platform ios --type argent \
  --build-id "$BUILD_ID" --max-duration-minutes 30 \
  --non-interactive --name "PR expo-bot"
```

Верифікаційний воркфлоу спирається на пре-пакейджені джоби `fingerprint`, `get-build`, а далі або `build` (нативка змінилась і готового білда немає), або `repack` — для JS-only змін, що на практиці найчастіший кейс.

Запустити воркфлоу руками з параметром:

```bash
eas workflow:run qa-swarm.yml -F pr_number=42
```

Тригер на фідбек із TestFlight описується так:

```yaml
on:
  app_store_connect:
    beta_feedback:
      types:
        - screenshot
```

Звідки це: офіційний пост Expo від 19 листопада, усі команди й конфіг — звідти, демо лежить у публічному репо `todo-app`. Сам не перевіряв.

Навіть без жодного агента `repack` замість повного білда на JS-only змінах плюс `--max-duration-minutes` на симуляторі — це просто дешевший CI. Решту можна прикручувати поступово.
