## ⚛️ React

**React [змерджив у react-dom API `browser()`](https://github.com/react/react/pull/37143) — офіційний спосіб сказати «цей компонент рендериться тільки в браузері»**

Досі такі шматки прикидались помилкою під час SSR, і логи забивались фейковими ерорами. Тепер `browser()` повертає usable-обʼєкт, який віддається в `use()` і чесно саспендиться на сервері:

```jsx
import {use, Suspense} from 'react';
import {browser} from 'react-dom';

function BrowserOnly() {
  use(browser());
  return <ClientContent />;
}

function App() {
  return (
    <Suspense fallback={<Fallback />}>
      <BrowserOnly />
    </Suspense>
  );
}
```

Обовʼязково всередині `Suspense` — інакше фатальна помилка (автори пишуть, що обмеження ще можуть послабити). У Server Components API немає взагалі: його прибрали з `react-server`-експортів.

У стабільний реліз це ще не приїхало — останній опублікований React це 19.2.8 від 21 липня. Але якщо шариш компоненти між вебом і RN, варто знати наперед: скоро `typeof window` чекати не доведеться.

## 📱 React Native та Expo

**React Native Firebase [випустив 26.1.0](https://github.com/invertase/react-native-firebase/blob/main/packages/app/CHANGELOG.md) — а разом з мажором 26.0 бібліотека повністю переїхала на TurboModules**

У 26.1 головне — резолв iOS-залежностей через SPM, а не тільки CocoaPods, плюс підняті нативні SDK (iOS 12.17.0, Android 34.16.0) і фікс крашів веб-авторизації.

Але справжня зміна сталась у 26.0: Auth, Database, Messaging, Installations, Phone Number Verification і сам App/Core переписали на Codegen TurboModules. Legacy Architecture більше не підтримується взагалі.

⚠️ **Міграція:** New Architecture обовʼязкова для всіх перелічених модулів, а на Android `makePlayServicesAvailable` тепер може реджектити проміс — обробляй. [Changelog](https://github.com/invertase/react-native-firebase/blob/main/packages/app/CHANGELOG.md)

Якщо ти вже на RN 0.82+, ти й так на New Arch — оновлюйся спокійно. Якщо десь лишився старий проєкт на legacy, 26.x для нього закритий назавжди.

**Mateusz Jastrzębski зробив [react-native-plain-text](https://github.com/mdjastrzebski/react-native-plain-text) — простий текст в обхід текстового пайплайна RN**

Компонент рендериться прямо в нативний віджет: `UILabel` на iOS, `TextView` на Android.

• **Що замінює:** звичайний `Text` з RN, але тільки для плоского рядка з одним стилем. Вкладених текстів, мішаних стилів, виділення і обробки натискань немає — це свідомий трейд-оф.
• **Наскільки стабільно:** у README статус beta, «API is stable enough to use». На npm вже 0.6.1 — релізи виходять кілька разів на тиждень. Потрібен Fabric; в Expo Go не працює, тільки dev client або bare.
• **Чим покращить:** цифри з README на 1000 вʼюх у release-білді — Android ~30% швидший маунт і ~33% менше памʼяті на вʼюху, iOS 13–21% швидше і 15–25% менше памʼяті.

```bash
npm install react-native-plain-text
```

Головний кейс очевидний — довгі списки, де в кожній комірці по три рядки тексту. Не заміна `Text` глобально, а точковий інструмент для гарячих екранів.

## 🧰 Бібліотеки й тулінг

**TanStack [зарелізив Table V9](https://tanstack.com/blog/announcing-tanstack-table-v9) — два роки роботи, нова плагінна архітектура і серйозні цифри**

Ядро переїхало на TanStack Store, фічі стали tree-shakable плагінами: таблиця, якій треба тільки сортування, більше не тягне фільтри, пагінацію і групування.

• середній час обробки core row model — на 79% менше
• retained heap — до 86% менше; на мільйоні рядків 2.71 GB → ~380 MB
• розмір самого пакета виріс з 14kb до 25kb, але конкретна таблиця виходить меншою за рахунок tree-shaking
• зʼявились виділення комірок діапазоном і спани по рядках/колонках

⚠️ **Міграція:** column sizing і resizing розділили на дві фічі, агрегацію і групування треба реєструвати явно (`rowAggregationFeature`, `columnGroupingFeature`). Для поступового переходу є deprecated-хук `useLegacyTable` з V8-подібним API, але він тягне всі фічі одразу. [Гайд для React](https://tanstack.com/table/latest/docs/framework/react/guide/migrating)

![TanStack Table V9](https://tanstack.com/cdn-cgi/image/width=1200,height=630,fit=cover,quality=80,format=auto/blog-assets/announcing-tanstack-table-v9/header.png)

9.0.0 вийшов 4 серпня, і за пʼять днів npm уже показує 9.1.2 — патчі сиплються щодня. Виглядає так, що варто дати релізу тиждень-два відлежатись, а вже потім планувати міграцію.

**TanStack паралельно відкрив [Charts](https://github.com/TanStack/charts) — граматику візуалізації з експериментальним адаптером для React Native**

• **Що замінює:** Victory Native, react-native-gifted-charts і подібне — але не завтра. Це framework-agnostic грамматика поверх гранульованих D3-примітивів, яка компілюється в renderer-neutral сцену; рендер у SVG, опційно Canvas.
• **Наскільки стабільно:** pre-alpha, у репо прямо написано «not ready for production use». Автор чесно каже, що проєкт написаний майже повністю за допомогою AI під наглядом. Пакет `@tanstack/react-native-charts` на npm має 0.8.0 і в описі позначений як experimental.
• **Чим покращить:** марки, трансформи, лейаути і рендерери лежать в окремих subpath-ах, тож у бандл їде тільки те, що реально юзаєш.

Для проду зарано, але сам факт, що TanStack робить чарти з першокласним RN-адаптером, — це те, за чим варто стежити. У RN нормальних чартів історично бракує.

## 💡 Рецепти

**Margelo розписали [повний пайплайн face recognition на пристрої](https://margelo.com/blog/on-device-face-recognition-react-native) поверх VisionCamera v5 — детекція, трекінг, вирівнювання, liveness і матчинг по ембедингах**

Ключова точка — новий `useFrameOutput` з VisionCamera v5, де вся конфігурація потоку задається одразу, а важка робота живе в C++:

```ts
const frameOutput = useFrameOutput({
  targetResolution: { width: 640, height: 480 },
  pixelFormat: 'yuv',
  dropFramesWhileBusy: true,
  onFrame(frame) { /* pipeline runs here */ }
})
```

Моделі — YuNet на детекцію, SFace на ембединги, MiniFASNet на liveness, інференс через ONNX Runtime або LiteRT.

Цифри з поста: детекція ~5ms (YuNet, вхід 128, Galaxy S21 Ultra), ембединг ~29ms (SFace в один тред), увесь пайплайн ~39ms на кадр. Тобто 30 fps з одним дорогим кадром на кожні десять. Точність — 95.94% на галереї з 5000 людей.

Джерело — інженерний блог Margelo від 30 липня, автори VisionCamera; цифри їхні, я їх не перевіряв. `dropFramesWhileBusy` і `targetResolution` тут головні, навіть якщо ніякого face recognition тобі не треба — це базовий рецепт «як не завалити камеру важким frame processor».
