## ⚛️ React

**React [задокументував `use(browser())`](https://react.dev/reference/react-dom/browser) — офіційний спосіб сказати «цей компонент рендериться тільки в браузері»**

Замість перевірок на `typeof window` і танців з `useEffect` плюс `mounted`-стейтом тепер є API: викликаєш `browser()` всередині `use()`, і на сервері рендер компонента зупиняється, лишаючи фолбек найближчого `Suspense`. У браузері `use(browser())` повертає `undefined`, і компонент рендериться як звичайно.

```jsx
import { use, useState } from 'react';
import { browser } from 'react-dom';

function SavedDraft() {
  use(browser('The draft is stored in localStorage.'));
  const [draft, setDraft] = useState(
    () => localStorage.getItem('draft') ?? ''
  );
  return <textarea value={draft} onChange={(e) => setDraft(e.target.value)} />;
}
```

Аргумент необов'язковий — це рядок-причина, який приїжджає як `cause` в `onBrowserBailout`. Поки що API живе в Canary і Experimental, стабільним стане в 19.3.

Разом з ним у [типах 19.3](https://github.com/DefinitelyTyped/DefinitelyTyped/pull/75429) з canary в stable переїжджають `ViewTransition`, `addTransitionType` і `ref` на `Fragment` — але наразі для react-dom, RN-рендерер отримає їх пізніше.

Прямо зараз RN-нику це не дає нічого. Але Fragment ref і ViewTransition — це фундамент, з якого потім виростуть нормальні переходи в RN, тож подивитись на форму API варто вже.

## 📱 React Native та Expo

**React Native [пропонує порізати публічний C/C++ API](https://github.com/react-native-community/discussions-and-proposals/pull/1018) на три рівні видимості**

RFC ділить хедери так:
• **Public** — стабільні між релізами, юзати можна
• **For Frameworks** — стабільні лише в межах мінорної версії
• **Private** — можуть змінитись будь-коли

Enforcement робиться хедер-гардами: `UmbrellaGuard.h` не дає інклудити публічні хедери повз umbrella, `FrameworksGuard.h` кидає ворнінг, `PrivateGuard.h` — hard error. Керують цим три макроси: `RN_UMBRELLA_INCLUDE`, `RN_BUILDING` і `RN_STRICT_API` — той самий opt-in-підхід, що вже знайомий по Strict TypeScript API.

Для авторів нативних модулів це переїзд з точкових інклудів на umbrella-хедери:

```cpp
// було
#include <react/renderer/runtimescheduler/RuntimeScheduler.h>
// стане
#include <React/RuntimeScheduler.h>
```

⚠️ **Міграція:** у першій фазі enforcement вимкнено за замовчуванням і вмикається флагом `RN_STRICT_API`, у другій стає стандартом. Окремого гайду ще немає — є [сам RFC](https://github.com/react-native-community/discussions-and-proposals/pull/1018).

Це відкритий пропозал, не реліз. Але якщо в тебе свій нативний модуль на C++, прочитати і закинути коментар зараз дешевше, ніж ловити hard error через два релізи.

## 🧰 Бібліотеки й тулінг

**Vitest [зарелізив 5.0](https://vitest.dev/blog/vitest-5) — з `vi.when()`, trace view і купою змінених дефолтів**

`vi.when()` — це мок, який відповідає по-різному залежно від аргументів, з deep equality і підтримкою асиметричних матчерів:

```ts
const findById = vi.fn()

vi.when(findById)
  .calledWith(1)
  .thenResolve({ id: 1, name: 'Ella' })
  .calledWith(expect.any(Number))
  .thenReject(new Error('not found'))
```

Друга помітна річ — trace view для Browser Mode: покроковий реплей тесту з DOM-снапшотами, працює і в UI, і в HTML-репортері, тобто в CI теж.

⚠️ **Міграція:** потрібні Vite 6.4+ і Node 22.12+. `clearMocks` тепер `true` за замовчуванням, асинхронні asserts без `await` валять тест, `vi.mock()` поза top-level кидає помилку замість ворнінга, `bench` переїхав у фікстуру всередині `test()`, локатори в Browser Mode строгі за замовчуванням. [Гайд](https://vitest.dev/guide/migration)

![Vitest 5](https://vitest.dev/og-vitest-5.jpg)

Jest-пресет у RN це не замінює. Але якщо в монорепі є веб-частина або пакет із чистою логікою — `vi.when()` знімає половину болю з мок-фабриками. Оновлюватись без поспіху: змінених дефолтів забагато, щоб робити це в п'ятницю.

**Apple [назвали дату кінця Rosetta](https://developer.apple.com/news/?id=w5ngl9k2) — macOS 27 буде останньою версією з підтримкою**

Що по датах:
• macOS 26.4 і новіші — користувач бачить системне сповіщення при запуску апки, яка тягне Rosetta
• macOS 27, цієї осені — останній реліз із Rosetta; Intel-only апки на Apple silicon просто не запустяться

Apple радять збирати universal binary і окремо достукатись до юзерів, щоб ті поставили нативну версію.

На iOS/Android-збірки це не впливає ніяк. Але якщо ти катаєш щось на react-native-macos або маєш десктопний компаньйон до мобілки — ось твій дедлайн. І це привід почистити x86-хвости в локальному тулчейні, поки є час.

## 💡 Рецепти

**Прогнати світлу і темну тему в одному Maestro-флоу**

Maestro 2.9 від 31 серпня додав те, що просили з 2023-го — керування темою прямо з флоу. Чотири команди: `setDarkMode`, `toggleDarkMode`, `assertDarkMode`, `assertLightMode`.

```yaml
appId: com.example.app
---
- launchApp
- setDarkMode: enabled
- assertDarkMode
- assertVisible: "Профіль"
- toggleDarkMode
- assertLightMode
- assertVisible: "Профіль"
```

`setDarkMode` бере обов'язковий аргумент — `enabled` або `disabled`. `toggleDarkMode`, `assertDarkMode` і `assertLightMode` аргументів не мають зовсім.

У тому ж релізі: Android WebView нарешті інспектується надійно (React, Vue, Angular, глибокі DOM-ієрархії вичитуються повністю), заморожені WebView на Android 16 більше не блокують тест, а в `config.yaml` зʼявилось виключення файлів через `!`.

Звідки: назви команд і синтаксис — з [довідника команд Maestro](https://docs.maestro.dev/reference/commands-available), решта — з [анонсу 2.9.0](https://maestro.dev/blog/maestro-cli-2-9-0). Сам флоу зібраний з цих команд: `appId` плюс `---` і `launchApp` — стандартна обгортка Maestro, але саме цей приклад цілком у джерелах не наводиться.

**Перевірити фолди і розміри екрана без миші — `adb emu` з термінала**

Rob Orgiu з Android-команди [показав](https://android-developers.googleblog.com/2026/08/emulator-adaptive.html) набір fire-and-forget команд емулятора: вони віддають контроль шелу одразу, тож їх зручно ставити в скрипт або в прогін перед комітом.

```bash
# скласти / розкласти фолдабл
adb emu fold
adb emu unfold

# поворот на 90 градусів за годинниковою
adb emu rotate

# постури: без аргументу — список, з ID — виставити (2 це tabletop)
adb emu posture
adb emu posture 2

# ресайз: без аргументу — доступні пресети (phone, unfolded, tablet)
adb emu resize-display
adb emu resize-display 1
```

Коли емуляторів кілька, цільовий вибирається як завжди:

```bash
adb -s <serial> emu <command> <parameter>
```

Звідки: команди дослівно з [посту Android Developers Blog](https://android-developers.googleblog.com/2026/08/emulator-adaptive.html) від 31 серпня.

Для RN це найдешевший спосіб перевірити, що лейаут не розсипається при зміні розміру і що стейт переживає configuration change — без ручного клікання по Resizable Emulator.
