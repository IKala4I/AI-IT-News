## 🚀 Моделі

**Alibaba [зарелізили Qwen3.8-Max](https://qwen.ai/blog?id=qwen3.8) — і вперше обіцяють відкрити ваги моделі Max-класу**

Цифри з анонсу:
• 2.4T параметрів MoE, ~95B активних на токен
• 1M контексту, текст плюс vision
• \$2 / \$6 за мільйон токенів

Головне тут не бенчмарки, а один рядок: наступного тижня Qwen обіцяють викласти ваги самого Max — для Max-лінійки такого ще не було — і разом з ним Qwen3.8-27B.

Спробувати вже можна в [Qwen Chat](https://chat.qwen.ai/?models=qwen3.8-max). Офіційний блог рендериться на клієнті, тож розміри й ціни — з анонсу Qwen і зведень; повного техрепорту поки немає.

Сьогодні на HN 900+ балів, і в коментарях чекають саме 27B: пишуть, що для локального дейлі-драйвера в цьому розмірі поки немає нічого схожого. Заяву про «10+ днів автономної розробки» там же розносять як маркетинг.

**MiniMax [відкрили ваги H3](https://huggingface.co/MiniMaxAI/MiniMax-H3) — omni-модель, яка генерує відео разом зі стерео-звуком за один прохід**

31 липня модель вийшла як API, 3 серпня приїхали ваги. H3-Base — 33B omni-трансформер: приймає текст, картинки, відео й аудіо в одному контексті, віддає відео до 2K і 4–15 секунд, де звук генерується разом з кадрами, а не накладається post-hoc.

Ліцензія власна — MiniMax H3 Community License, не Apache. Два чекпоінти під різні задачі: FL2VA (текст, перший і останній кадр) та Ref2VA (генерація за референсами). Частина стека лишилась закритою: H3-Context-IR і H3-Regenerate-2K доступні тільки через API.

ComfyUI [підхопив у день релізу](https://blog.comfy.org/p/minimax-h3-day-0-support-in-comfyui) — нативні ноди й шість готових воркфлоу. Найменший int8-варіант ваг — 19.5 GB, повний bf16 — 61.7 GB.

![MiniMax H3 у ComfyUI](https://substack-post-media.s3.amazonaws.com/public/images/67ff80a9-2436-4749-a553-5f6c8c77e23c_1920x1080.png)

Відкриті ваги на відео-модель такого рівня — рідкість. Якщо треба ганяти генерацію пачками локально й без API-рахунку, це зараз найсерйозніший варіант.

## 🛠️ Інструменти

**Anthropic [виклали Claude Security плагіном для Claude Code](https://code.claude.com/docs/en/claude-security) — багатоагентний скан коду з патчами, які застосовуєш сам**

```
/plugin install claude-security@claude-plugins-official
/reload-plugins
```

Далі все живе за однією командою `/claude-security`, яка відкриває меню з трьох робіт: скан усього репозиторію, скан діфа (гілка, PR або окремий коміт) і генерація патчів за знайденим.

Влаштовано так: команда агентів будує threat model, шукає вразливості, і кожну знахідку окремо перевіряє незалежний верифікатор — тому в звіті мало сміття. Результати лягають у `CLAUDE-SECURITY-<timestamp>/` з власним `.gitignore` всередині. Патчі ніколи не застосовуються автоматично:

```bash
git apply CLAUDE-SECURITY-<timestamp>/patches/F1.patch
```

Потрібні Claude Code 2.1.154+, платний план і `python3` 3.9.6+. Скан їсть токени з твого ліміту. Це офіційна фіча з документації, сам не ганяв.

Рівно та штука, яку варто кинути на легасі-репозиторій перед тим, як щось у ньому чіпати.

## 📌 Рухи й безпека

**JFrog [розібрали 55 «критичних» CVE на SQLite](https://research.jfrog.com/post/sqlite-critical-cves-or-llm-slops/) — 54 з них виявились галюцинаціями LLM**

У липні акаунт `programmervuln` на GitHub опублікував пачку advisory на SQLite, і вони спокійно доїхали до CVE: -51296, -51297, -51300, -51302, -51303, -51304 та інші.

Що знайшли дослідники:
• посилання на функції, яких у цих версіях SQLite не існує
• номери рядків за межами файлу — рядки 3555–3575 у файлі на 2706 рядків
• PoC, які падають ще на етапі парсингу
• «фікси» у версіях, де немає жодної відповідної зміни коду

Ключова деталь: публічна форма MITRE ніяк не верифікує особу того, хто подає заявку.

Висновок неприємний: червоний критикал від dependency-сканера більше не є сам по собі приводом гальмувати реліз. Тепер треба йти на сторінку вендора й перевіряти руками, чи ця дірка взагалі існує.
