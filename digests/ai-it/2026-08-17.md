## 🛠️ Інструменти

**Cursor [запустив Origin](https://cursor.com/changelog/origin-code-hosting) — власний хостинг коду з PR-ами, який двосторонньо синкається з GitHub**

Early beta, розкочують сьогодні на всі платні плани (крім enterprise-орг, де адмін вимкнув). Те, що вже є:
• вкладка **Codebase** — створюєш репо, отримуєш `cursor.com/codebase/&lt;назва&gt;`, пушиш через CLI
• GitHub-репозиторії живуть поруч: обираєш, які синкати, і їх видно в Cursor у реальному часі
• pull requests із таймлайном, комітами, чеками і дифом
• коменти в PR ходять в обидва боки — відповів на GitHub, за секунди видно в Cursor
• apps: Vercel робить preview-деплой на кожен PR, Depot і Buildkite крутять твої ж GitHub Actions

Пуші синкнутих репо й далі йдуть у GitHub — він лишається source of truth.

Головне тут не хостинг, а те, що агент тепер сидить у тому ж вікні, де код і PR: питаєш про код, який гортаєш, і він же може оновити PR чи запушити гілку. Агентні фічі обіцяють «скоро» — поки що це радше акуратний GitHub-фронтенд із вбудованим Cursor.

**DuckDB [показали превʼю v2.0](https://duckdb.org/2026/08/17/duckdb-20-highlights) — той самий DuckDB, але тепер його можна підняти сервером**

10 000 комітів після v1.5, реліз восени, превʼю-білди вже є. Найбільша зміна — розширення `quack` виходить зі стану превʼю: будь-який процес DuckDB віддає свої бази по мережі, будь-який інший чіпляється до нього новим `CONNECT`:

```sql
-- сервер
CALL quack_serve(token = 'my_token');

-- клієнт
ATTACH 'quack:server.example.com' AS qk (TOKEN 'my_token');
CONNECT qk;
SELECT count(*) FROM events;
DISCONNECT;
```

`CONNECT` працює не тільки з Quack: новий remote pushdown optimizer шле SQL прямо в PostgreSQL і MySQL, замість тягнути таблиці до себе.

```sql
CONNECT 'postgres://localhost/mydb';
SELECT count(*) FROM orders;  -- рахується на боці PostgreSQL
DISCONNECT;
```

Решта коротко: тригери `BEFORE`/`AFTER`, `VARIANT` зі shredded-виконанням, асинхронний I/O для мережевих сховищ, рекурсивні CTE ~40× швидше, новий PEG-парсер SQL і стабільний extension API.

Для локального аналізу логів і CSV нічого не змінюється. Але «DuckDB як спільний сервер для команди» — це вже інша ніша, куди раніше йшли по Postgres або ClickHouse.

## 💡 Рецепти

**Перше, що треба зробити з Qwen 3.8 27B, — [збити reasoning з дефолтного `xhigh`](https://simonwillison.net/2026/Aug/16/qwen-38-27b/)**

Модель ми вже згадували 14 серпня. Апдейт від Simon Willison, який три дні ганяв її на M5 Max і DGX Spark: дефолт у неї — `xhigh`, і це катастрофа для локального заліза. Пелікан на велосипеді в SVG: **21 хвилина** і 22 276 reasoning-токенів проти **137 секунд** з вимкненим reasoning. На промпт «draw an svg of a circle» вона пішла проєктувати композицію в стилі Баугауз.

Офіційні рівні з доків Qwen — `xhigh` (дефолт), `medium`, `low`. Друге: у LM Studio дефолтні 8 192 токени контексту вона зʼїдає самим думанням, вантаж із повними 262 144.

Далі її реально можна саджати на кодинг-агента. Simon підняв модель у LM Studio і підчепив до Pi через `~/.pi/agent/models.json`:

```json
{
  "providers": {
    "spark": {
      "baseUrl": "https://spark-18b3.tail68a31.ts.net/v1",
      "api": "openai-responses",
      "apiKey": "dummy",
      "models": [
        { "id": "qwen3.8-27b", "reasoning": true }
      ]
    }
  }
}
```

```bash
pi --provider spark --model qwen3.8-27b
```

Сам не тестив; конфіг і цифри — з поста Simon, рівні `reasoning_effort` він цитує з офіційних доків Qwen. Нюанс від нього ж: на bounding boxes і на генерації цілого UI reasoning таки допомагає — без нього тул виходив майже робочий, але з боксами не в тому місці. Тобто `low` як старт, а не «вимкнути й забути».

## 📌 Рухи й безпека

**Wiz [розібрали кейс](https://www.wiz.io/blog/red-agent-snowflake-copilot-cicd-bug), де GitHub Copilot Autofix сам створив інʼєкцію у workflow Snowflake**

18 червня коміт, співавтором якого вказано Copilot Autofix, «полагодив» `jira_issue.yml` у публічному репо `snowflakedb/snowflake-connector-net`. Полагодив так, що прибрав робочий безпечний патерн і поставив пряму інтерполяцію в shell:

```diff
- env:
-     ISSUE_TITLE: ${{ github.event.issue.title }}
- run: jq -n --arg title "$ISSUE_TITLE" ...
+ run: TITLE=$(echo '${{ github.event.issue.title }}' | sed ...)
```

`sed` тут екранує вже **після** підстановки GitHub, тож одинарна лапка в заголовку тікета виходить із `echo` і виконує будь-яку команду. Тригер — `issues: opened`, тобто будь-який користувач GitHub. Умова `if:` виглядала захистом, але на issues-івентах `github.event.pull_request` завжди `null`, і гейт був завжди відкритий.

Через пʼять днів це знайшов автономний агент Wiz і витягнув Jira-токен `qa@snowflake.net` — читання по інженерних, compliance і bug-bounty проєктах. Snowflake закрив того ж дня, 23 червня, і ротував креденшел.

Мораль не про Copilot і не про Snowflake. AI-фікс безпеки — це такий самий діф, який треба читати, а `${{ }}` всередині `run:` варто ловити лінтером, а не очима.
